Redis internals · Quick reference

Single-Threaded Event Loop

Core idea: Redis executes ordinary commands sequentially on its main thread. It does not wait for each client’s network transmission to finish; the OS and socket buffers handle much of the network waiting.

1. The critical loop

while Redis is running:
    collect ready socket events

    for each connection that needs attention:
        read available bytes
        parse complete command(s)
        execute command(s) on the main thread
        put response bytes in the output buffer

        if the socket can accept data:
            write pending response bytes

    return to the event loop

Important: This is simplified pseudocode, not Redis’s literal source code. Real Redis also handles timers, client state, incomplete commands, pending writes, and other server work.

2. What happens, in order?

1 · Client sends a commandGET user:123 travels over TCP.
↓
2 · OS receives network dataTCP/socket buffers can hold bytes while Redis is busy with another command.
↓
3 · Event loop notices readinessThe OS notifies Redis which sockets are ready to read or write. Redis need not continuously poll every idle connection.
↓
4 · Main thread reads and parsesRedis reads available bytes. If the command is incomplete, it waits for more data; it cannot execute a partial command.
↓
5 · Main thread executesFor GET user:123, Redis looks up the key in memory and obtains the result.
↓
6 · Prepare and send the replyRedis encodes the result and buffers it. It writes bytes when the socket can accept them; remaining bytes can wait for a later writable event.
↓
7 · Continue with ready workThe event loop handles other ready connections or buffered commands, then waits for/collects more events as needed.

3. Where do other requests wait?

OS / TCP receive buffer

Incoming bytes received from the network but not yet read by Redis.

Redis input buffer

Bytes Redis has read, possibly containing a partial command or several commands.

Redis output buffer

Response bytes prepared but not yet fully written to the socket.

There is not necessarily one giant central queue containing every client request. Waiting data can exist at different stages. All buffers are finite; if Redis falls behind, latency and memory use can rise, and clients may eventually time out or disconnect.

4. Why can one thread be so fast?

  • In-memory data: common reads and writes avoid disk access for each operation.
  • Less synchronization: sequential command execution avoids much of the locking needed when multiple threads modify shared data structures.
  • Event-driven I/O: many connections can be monitored without one thread per client or repeated checks of every idle socket.
  • Small per-command work: many commands are simple and complete quickly.
  • Pipelining: clients can send several commands without waiting for a round trip after each one.

5. The mental model

Main thread: read → parse complete command → execute → prepare reply.

Event loop / OS: identify ready sockets; network buffers absorb some waiting; send replies when possible.

Then: process other ready work. Command execution is sequential, while network activity for different clients can overlap.

Limit: A long-running command or script can block the main command thread and delay other commands. Single-threaded does not mean unlimited throughput, nor does it mean commands run in parallel.

Redis version and configuration affect networking details. This guide describes the core mental model rather than every implementation detail.
