01Redis Fundamentals

Mental model: Redis is a data-structure server. One thread executes commands one at a time against structures that live in RAM. Everything else (persistence, replication, clustering) is built around that core.

Beginner

#1 — What is Redis?

Redis (REmote DIctionary Server) is an in-memory key-value store that holds rich data structures, answers in microseconds, and can optionally persist to disk.

You talk to it over TCP with a simple text protocol (RESP) on port 6379. Unlike a plain key-value cache (where values are opaque blobs), Redis understands the value: a list, a hash, a sorted set. So you can ask the server to do something with the data (ZINCRBY, LPUSH, SINTER) instead of reading it, changing it in your app and writing it back.

What people use it for

  • Cache in front of a slower database or API (the most common use).
  • Session store, shopping carts, feature flags.
  • Counters and rate limiters (atomic INCR).
  • Leaderboards (sorted sets), queues (lists/streams), pub/sub messaging.
  • Distributed locks and coordination primitives.

Key properties

  • In-memory: data lives in RAM; disk is only for durability and restarts.
  • Single-threaded command execution: every command is atomic; no two commands run at the same time.
  • Optional persistence: RDB snapshots and/or AOF log. You can also run it with none.
  • Replication, Sentinel, Cluster provide copies, failover and sharding.

Senior

#1 — Why is Redis so fast?

Four things stack up: data in RAM, purpose-built in-memory data structures, a single-threaded event loop that never takes a lock, and a trivially cheap protocol. After that the bottleneck is the network, not Redis.

1. Memory instead of disk

RAM access is around 100 ns; a random SSD read is around 100 µs; a spinning disk, ms. Redis never has to page data in from disk for a read. It also never needs a buffer pool, page cache logic or B-tree page splits.

2. Data structures designed for RAM, not for disk

Disk databases pick structures that minimise seeks (B-trees). Redis picks structures that minimise CPU and pointer chasing:

  • Hash table with incremental rehashing: O(1) key lookup, and resizing never stops the world (two tables migrate bucket by bucket).
  • SDS (simple dynamic strings): length stored, so STRLEN is O(1), binary-safe, amortised appends.
  • Listpack / intset / quicklist: small collections are stored in one contiguous block, which is cache-friendly and memory-cheap. They convert to hashtable/skiplist when they grow past thresholds.
  • Skiplist + hashtable for sorted sets: O(log n) range and rank queries, O(1) score lookup by member.

3. Single-threaded event loop

One thread multiplexes thousands of sockets with epoll (Linux) / kqueue (BSD). It reads a request, executes it to completion, writes the reply, moves on. Consequences:

  • No locks, no mutexes, no context switches between threads, no cache-line contention. A command costs a few hundred nanoseconds to a few microseconds of pure CPU.
  • Every command is atomic for free. This is why INCR and Lua scripts are safe without extra machinery.
  • The price: one slow command blocks everyone. KEYS *, SMEMBERS on a million-member set or a 5-second Lua script stalls every client.

4. Cheap protocol and batching

RESP is length-prefixed text; parsing is nearly free. Pipelining lets a client send many commands in one packet, so the per-command cost shrinks to CPU only (see topic 11).

Where the time really goes

What changed in recent versions

Redis 6 added I/O threads that only do socket reads/writes and protocol parsing in parallel, while the main thread still executes commands serially. Redis 8 improved this further. Throughput on a big box rises, but the single-writer execution model, and its atomicity guarantee, stays.

Interview answer"RAM, efficient structures, no locks thanks to a single-threaded event loop, simple protocol. Typical throughput is 100k+ ops/s per core, so in practice the network RTT is the limit."
Staff

#1 — If Redis is so fast, why not put everything in Redis?

Because speed is bought with RAM, and RAM is expensive, bounded, and weakly durable. Redis is excellent at hot, derived, simply-shaped data; it is a poor system of record for large, relational, queried-in-many-ways, must-not-lose data.

A decision frame

Good fit for Redis
  • Derived/recomputable data (cache)
  • Hot working set that fits in RAM
  • Latency SLO under a few ms
  • Loss of the last second is tolerable, or reconstructable
  • Access by key or a small set of known patterns

  • System of record with strict durability
  • Large datasets with a cold tail
  • Ad-hoc queries, joins, reporting
  • Strong consistency across entities
  • Unbounded growth (logs, history)
Staff-level answerTreat Redis as a latency-optimisation layer in front of a durable store, or as the primary store only for data whose loss window and size you have explicitly accepted (sessions, rate limits, leaderboards, ephemeral queues). Put another way: for every key class, ask "if this vanished right now, what is the recovery path and how long does it take?" If the answer is "we lose business data", it does not belong only in Redis.

There are middle paths when you want Redis semantics with more capacity: tiered storage (Redis on Flash / Auto Tiering, vendor products), or databases that speak the Redis protocol but store on disk. These trade latency for cost and are a different product decision, not the default OSS Redis.

Senior

#2 — How do you choose between Hash, String, Set and Sorted Set?

Choose by access pattern: opaque value → String; object with partial reads/updates → Hash; uniqueness and membership → Set; ordering, ranking or time-range queries → Sorted Set.

String vs Hash for objects

  • String (JSON blob): one round trip, simplest, best when you always read the whole object. Updating one field means read-modify-write (race-prone) and rewriting the whole value.
  • Hash: HGET/HSET/HINCRBY a single field atomically, no serialisation, and small hashes are stored in a listpack (very compact). Beats a String per field by a large factor in memory because each top-level key costs ~50–100+ bytes of overhead. Limitations: values are flat strings (no nesting), and until Redis 7.4 you could not expire individual fields (HEXPIRE now exists).
  • RedisJSON: nested documents with path updates when you really need nesting.

Set vs Sorted Set

  • If you only need membership and uniqueness, Set is cheaper and O(1). SINTER on two sets answers "users who are in both groups".
  • If you need ordering, rank, top-N, or "everything between score A and B", use a Sorted Set. Cost: skiplist + dict, so noticeably more memory per member, O(log n) writes.
  • Time-ordered data: score = unix timestamp; trim with ZREMRANGEBYSCORE.

03Cache-Aside Pattern

Mental model: the application, not the cache, owns the logic. Redis is just a lookaside table; the DB stays the source of truth.

Beginner

#3 — How does Redis caching normally work?

The app asks Redis first; on a hit it returns immediately; on a miss it loads from the database, stores the result in Redis with a TTL, and returns it. On writes it updates the DB and removes (or updates) the cached copy.

value = redis.get(key)
if value is not null:
    return deserialize(value)          # hit
row = db.query(id)                     # miss
redis.set(key, serialize(row), ex=300 + random(0, 60))
return row

def update(id, data):
    db.update(id, data)
    redis.delete(key)                  # next read refills

Why people like it

  • Resilient: if Redis dies, the app still works (slower), because the DB is authoritative.
  • Only hot data occupies memory.
  • Simple, no special infrastructure; works with any DB.
Senior

#3 — What problems does cache-aside introduce?

The cache and the DB are two separate stores updated by application code, so you inherit every dual-write problem: stale reads, race conditions, stampedes, penetration, avalanches, cold starts and a dependency on Redis availability.

TakeawayCache-aside is eventually consistent, not consistent. Design the TTL as the upper bound on staleness you accept, and make every invalidation best-effort with the TTL as the net.

#3 — When would you avoid cache-aside?

When correctness or load characteristics make "application checks, then fills, then hopes to invalidate" the wrong shape: strong consistency needs, write-heavy or low-reuse data, very expensive recomputation, or when the DB cannot survive a miss storm.

Concrete "avoid" signals

  • Read-your-writes is a hard requirement (balances, inventory, permissions). Read from the DB primary, or use write-through with versioning.
  • Low hit rate (below roughly 70–80%): unique per-user data read once, huge keyspace. The cache adds latency and cost without relief.
  • Write-heavy: every write invalidates; you churn the cache and gain nothing.
  • Miss is catastrophic: recomputation takes seconds and the DB cannot handle concurrent misses. Prefer refresh-ahead or precompute so requests never trigger loads.
  • Multiple services write the same entity: scattered invalidation code will diverge. Centralise via CDC or one owning service.
  • Working set larger than affordable memory: you thrash. Cache a derived summary, or shrink the problem (pagination, projections).
Staff-level answerCache-aside is the default, not a law. Pick the pattern from (a) staleness budget, (b) write/read ratio, (c) cost of a miss, (d) who writes. If the staleness budget is zero, do not cache. If the cost of a miss is high, never let the request path perform the load.

04TTL and Expiration

Mental model: a TTL is a deadline stored next to the key, not a timer. Redis checks deadlines lazily and by sampling, so "expired" and "deleted" are two different moments.

Beginner

#4 — What is TTL?

TTL (time to live) is the number of seconds a key may live. When it runs out, Redis treats the key as gone, and reads return nil.

SET session:abc "data" EX 3600     # set value and TTL together (seconds)
SET k v PX 1500                    # milliseconds
EXPIRE k 60                        # add or change TTL on an existing key
EXPIREAT k 1767225600              # absolute unix time
TTL k      # seconds left; -1 = no TTL; -2 = key does not exist
PTTL k     # same in milliseconds
PERSIST k  # remove TTL, key lives forever
GETEX k EX 60   # read and renew TTL in one command (6.2+)

Things beginners trip on

  • Plain SET on an existing key erases its TTL. Use SET k v KEEPTTL or pass EX again.
  • Keys have no TTL by default (TTL returns -1). A cache key written without EX lives until eviction or manual delete, a common memory leak.
  • TTL belongs to the whole key. Before Redis 7.4 you could not give hash fields or set members their own TTL; 7.4 added HEXPIRE for hash fields.
  • Typical uses: cache entries, sessions, one-time codes, rate-limit windows, locks.
Senior

#4 — Does Redis delete every expired key exactly when its TTL reaches zero?

No. Redis never runs a timer per key. It deletes expired keys in two ways: lazily when someone touches the key, and by a sampling background job. A key can be logically expired but still occupy memory for a while.

What this means in practice

  • Memory is not freed on the dot. Millions of keys expiring at once can leave memory high for seconds to minutes. INFO stats shows expired_keys; INFO keyspace shows keys vs expires.
  • DBSIZE and KEYS/SCAN can still count keys that are logically expired but not yet deleted.
  • Replicas do not expire keys by themselves. The master emits an explicit DEL (also written to the AOF) when it expires a key. Replicas hide logically expired keys from reads, but only delete when the master tells them to. This keeps data consistent between nodes.
  • Persistence: expired keys are skipped when loading an RDB on a master; the AOF gets the DEL.
  • Wall clock matters. Deadlines are absolute timestamps. If the system clock jumps forward, many keys expire at once; backwards, keys live longer. A replica with a skewed clock may treat keys as expired differently.
  • hz (default 10) controls cron frequency; dynamic-hz adjusts it with client count. Raising hz expires faster but costs idle CPU.
  • Removing a huge key by expiry is a blocking delete unless lazyfree-lazy-expire yes is set.
Staff

TTL turns time into a load generator. Synchronised expiry causes stampedes and expiry storms, sliding TTLs amplify writes, short TTLs destroy hit rate, forgotten TTLs leak memory, and expiry work competes with your requests on the single thread.

05Cache Stampede

Mental model: a cache is a shock absorber for the database. A stampede is the moment the absorber disappears for one hot key and every request becomes a database request.

Beginner

#5 — What is cache stampede?

A popular key expires, hundreds of requests miss at the same moment, and all of them recompute the same value from the database at once. Also called thundering herd or dogpile.

It matters most for keys that are both very hot and expensive to rebuild: home-page data, a global config, a big aggregate query.

Senior

#5 — How do you prevent it?

Make sure only one caller rebuilds a key (single-flight or a lock), keep serving an old value while it rebuilds (stale-while-revalidate), refresh early or randomly before expiry, and spread TTLs with jitter.

1. Single-flight (in-process request coalescing)

Within one app instance, concurrent misses for the same key share one in-flight load. Go's singleflight, .NET Lazy<Task> per key or a keyed SemaphoreSlim, Java Caffeine's loading cache. Cheap and effective but per-instance: 50 pods still send 50 loads.

2. Distributed mutex on miss

v = GET key
if v is null:
    if SET lock:key token NX PX 10000:       # winner rebuilds
        v = load_from_db()
        SET key v EX ttl
        release lock (compare token, then DEL)
    else:
        sleep 20-50 ms with jitter, retry GET (bounded), else serve fallback

Guarantees one rebuild across the fleet. Costs: extra round trips, waiters are blocked or must retry, the lock needs its own TTL and a safe release (topic 17), and a crashed winner delays everyone until the lock TTL.

3. Stale-while-revalidate (logical expiry)

Store the value with a soft deadline inside the payload and a longer hard Redis TTL. After the soft deadline, one caller refreshes (guarded by a lock or single-flight) while everyone else immediately gets the stale value.

4. Probabilistic early expiration (XFetch)

Each reader independently decides, with rising probability as expiry nears, to recompute early. No lock, no coordination:

# delta = how long the last recompute took, beta = 1.0 (higher = earlier)
if now - delta * beta * ln(random()) >= expires_at:
    recompute()

Expensive recomputes (large delta) start earlier; cheap ones start late. The expected number of simultaneous recomputes stays near 1.

5. Other layers of defence

  • TTL jitter so different keys do not synchronise.
  • Refresh-ahead / background warmer for a known small hot set, so users never trigger loads.
  • Negative caching for "not found" (short TTL) so missing keys do not stampede either.
  • DB protection: bulkhead / concurrency limit / circuit breaker so even a stampede cannot take the DB down.
  • Never-expire hot keys updated by a writer or job (explicit invalidation instead of TTL).
Staff

#5 — Which technique would you choose?

My default is layered: single-flight per instance + stale-while-revalidate + TTL jitter. Add a distributed lock only when the recompute is expensive and the fleet is large; use XFetch when coordination is unwanted; precompute for the handful of critical keys.

How I decide

  1. How stale can it be? If minutes are fine, SWR removes latency from the equation and the problem mostly disappears.
  2. How costly is one rebuild? Milliseconds: single-flight + jitter is enough. Seconds or DB-heavy: add a cross-instance guard (lock or leader refresh).
  3. How many keys are hot? A handful: dedicated refresher. Thousands with a long tail: XFetch/SWR, no per-key machinery.
  4. What happens if the guard fails? Lock holder crashes, Redis blips. The fallback must be "serve stale or degrade", never "everyone rebuilds".
  5. Can the DB survive the worst case anyway? Put a concurrency limit in front of it; the stampede protection is then an optimisation, not the last line.
Pitfalls to nameLock with no TTL (deadlock); lock TTL shorter than rebuild time (two builders); waiters spinning in a tight retry loop (still a herd, now on Redis); all waiters waking at lock release (herd round two, so add jitter); SWR with no hard TTL (stale forever when the refresher is broken).

06Cache Invalidation

Mental model: the cache is a copy; invalidation is the protocol that keeps the copy honest. You are choosing which anomalies you can live with, not eliminating them.

Beginner

#6 — What is cache invalidation?

It is removing or updating cached data when the original data changes, so users do not keep seeing old values.

Example: a product price changes in the DB from 100 to 120. If Redis still holds 100, customers see the wrong price until that cache entry is invalidated (deleted or overwritten) or expires. The famous joke ("there are only two hard things in computer science: cache invalidation and naming things") is true because the cache and the DB are different systems, and nothing makes the change atomic across both.

The two basic strategies

  • Time-based: let a TTL expire it. Simple and self-healing, but data can be stale for up to the TTL.
  • Event-based: when data changes, delete or update the cache entry. Fresh, but you must never forget a code path, and failures leave stale data.

In practice you use both: explicit invalidation for freshness plus a TTL as the safety net.

Senior

#6 — What's dangerous about "update DB then delete Redis"?

The two steps are not atomic. The delete can fail or be skipped, and a concurrent reader can re-populate the cache with the old value after your delete, especially when the reader hits a lagging replica. The cache then stays stale until TTL.

Failure modes

  1. Delete fails after the DB commit. Process crash, timeout, Redis blip. DB is v2, Redis is v1, no one knows. Stale for the full TTL (or forever if there is no TTL).
  2. Reader refills with the old value (race). A reader read v1 before the update; it writes v1 into Redis after the writer's delete (diagram in topic 3).
  3. Read replica lag. After the write and delete, a reader misses the cache and reads from a DB replica that has not received the update yet, caches old data. This is the most common real-world cause.
  4. Delete before commit. If code deletes the key inside the transaction (or before commit completes), a reader can refill from the old committed row, then your commit lands: stale.
  5. Cluster/partial failures. Delete reached the primary but the failover promoted a replica that did not get it.
  6. Multiple writers / services. Another service updates the same row and never knows the cache key.
Why not delete first, then update the DB?Worse: between the delete and the DB commit, a reader refills the cache with the old row, and the commit leaves it stale. Always: DB commit, then invalidate.

Mitigations (combine them)

  • TTL on everything. Bounds every stale window. Non-negotiable safety net.
  • Reliable invalidation: retry deletes with backoff, or use an outbox table (write "invalidate key X" in the same DB transaction, and a worker deletes after commit) or CDC.
  • Delayed double delete: delete after commit, then delete again after a delay larger than the reader's DB latency + replica lag (e.g. 500 ms–1 s). It kills the race but is heuristic.
  • Read from primary for refills shortly after writes, or route refills to the primary when the key was recently invalidated.
  • Versioned writes: store a version (row version / updated_at) with the value; refuse to overwrite a newer version. Do this atomically with Lua:
-- KEYS[1]=cache key, ARGV[1]=version, ARGV[2]=payload, ARGV[3]=ttl
local cur = redis.call('HGET', KEYS[1], 'v')
if (not cur) or tonumber(ARGV[1]) > tonumber(cur) then
  redis.call('HSET', KEYS[1], 'v', ARGV[1], 'd', ARGV[2])
  redis.call('EXPIRE', KEYS[1], ARGV[3])
  return 1
end
return 0
  • Leases (as in Facebook's memcache paper): on a miss, the cache hands the first reader a token; a delete invalidates outstanding tokens, so a stale refill is rejected. Implement with a short-lived marker key.
  • Single owner: only one service writes the entity and owns its cache keys.
Staff-level answer"Update then delete" is the best simple default, and it is still only eventually consistent. Make it safe by (1) TTL backstop, (2) retries or CDC so a delete is never lost, (3) a defence against stale refills (versioning, double delete, primary reads), and (4) a clear statement of the staleness bound you accept.

07Redis Memory

Mental model: RAM is the capacity limit, maxmemory is the policy line, and the eviction policy decides what happens when you cross it.

Beginner

#7 — Why is Redis memory management important?

All data lives in RAM, so memory is the hard capacity limit. If you run out, Redis evicts data, rejects writes, or the OS kills it or starts swapping, which turns microsecond latency into seconds.

What goes wrong without it

  • No maxmemory set: Redis grows until the OS OOM killer ends the process. Everything in RAM that was not persisted is lost, and the failure is abrupt.
  • Swapping: if the OS pages Redis to disk, each access costs milliseconds. Latency collapses.
  • noeviction reached: writes fail with OOM command not allowed when used memory > 'maxmemory', while reads still work. Apps start throwing errors.
  • Fork headroom: RDB snapshots and AOF rewrites use fork() with copy-on-write. Under heavy writes the child can need up to the whole dataset size again. Budget for it.
  • Money: memory is the biggest cost driver, so wasteful keys directly cost dollars.

Basic setup

maxmemory 6gb                       # hard ceiling for dataset (leave room on an 8 GB host)
maxmemory-policy allkeys-lru        # what to do at the ceiling
# host: vm.overcommit_memory=1, disable swap or keep it tiny, disable THP
Rule of thumbSet maxmemory to roughly 60–75% of the box or container memory when persistence or replication is on, to leave room for fork copy-on-write, client buffers, replication backlog and fragmentation.
Senior

#7 — What are eviction policies?

They decide what Redis removes when memory hits maxmemory: nothing (return errors), or some keys chosen by recency, frequency, randomness or soonest TTL, from all keys or only keys that have a TTL.

How the sampled algorithms work

  • Approximate LRU: every key stores a 24-bit last-access clock. Redis samples maxmemory-samples random keys and evicts the oldest. 5 is cheap and decent; 10 is very close to true LRU; no global list is maintained (that would cost memory and CPU on every read).
  • LFU (4.0+): the same 24 bits hold a 16-bit decay time and an 8-bit logarithmic access counter (Morris counter). lfu-log-factor (default 10) controls how fast it saturates; lfu-decay-time (default 1 minute) halves the counter over time so old popularity fades. LFU resists scans (a one-time full read does not pollute the cache).
  • TTL: among sampled keys with a TTL, evict the one closest to expiry.
  • Random: no metadata cost; fine when access is uniform.

Details that matter

  • noeviction is the default. A cache with it will start failing writes at the limit.
  • Replica output buffers and the AOF buffer are excluded from the eviction calculation, so a flood of writes cannot make Redis evict its own replication stream.
  • Eviction work happens on the main thread. Evicting many large keys at once adds latency (lazyfree-lazy-eviction yes helps).
  • Monitor evicted_keys, keyspace_hits, keyspace_misses, and used_memory vs maxmemory.
Staff

#7 — How do you choose an eviction policy?

Start from what is stored. Pure cache: allkeys-lfu (skewed popularity) or allkeys-lru (recency). Mixed with must-keep data: volatile-* with disciplined TTLs, or better, separate instances. Queues, locks, sessions you cannot lose: noeviction and size properly.

Staff-level considerations

  1. Do not mix durable and cache data on one instance. A single policy cannot serve both. Two instances (or two clusters) give two policies and two blast radii. Eviction of a lock key or a stream entry is a correctness bug.
  2. Measure, do not guess. Compare hit ratio under LRU vs LFU in staging with replayed traffic. LFU wins on skewed traffic; LRU wins when the working set shifts quickly (LFU can hold stale-popular keys, though decay mitigates it).
  3. Eviction as a signal. A steady evicted_keys with a falling hit ratio means undersized memory, not a policy problem. A cache that evicts constantly while the DB is cold is fine; one that evicts while hit ratio drops is thrashing.
  4. Size for the fork. maxmemory counts the dataset, not RSS. Fragmentation, client buffers, backlog, and COW come on top.
  5. Sampling cost. Raising maxmemory-samples improves accuracy at some CPU. Test before raising on a hot box.
  6. Failure mode design. What happens in the app on an OOM error under noeviction? Decide: shed load, degrade, or fail the write. Do not discover it in production.
  7. Eviction storms. A burst of large writes can evict many keys in one pass, hurting both latency and the hit ratio. Cap value size.
Staff-level answer"Policy follows the data's loss tolerance. Cache: allkeys-lfu, validated by hit-ratio tests, on its own instance. Anything that must not vanish: noeviction on a separately sized instance with alerts at 70–80% memory."

08Memory Optimization

Mental model: bytes you store are the small part. Pointers, headers, allocator rounding and fragmentation are the rest, and they are paid per key.

Beginner

#8 — Why can a small Redis value consume more memory than expected?

Every key carries fixed overhead: a hash-table entry, an object header, a string header, an optional expiry entry, plus allocator rounding. A key with a 10-byte value can easily use 70–100+ bytes in total.

Practical consequences

  • 100 million small keys cost gigabytes of overhead. Storing 1M counters as 1M String keys is far more expensive than one Hash with 1M fields, or hashes bucketed into groups of ~100 fields (a well-known trick, which keeps each hash in compact listpack encoding).
  • Long key names cost too. user:profile:settings:notifications:email:42 is repeated per key. Short, consistent prefixes save real memory at scale.
  • Serialization format: JSON text is verbose; MessagePack/protobuf, or compressing big values (LZ4/zstd), cuts memory and network.
  • Encoding choice: small collections are listpack/intset (compact); big ones are hashtable/skiplist (several times more per element).
  • Other consumers: client buffers, replication backlog, AOF rewrite buffers, Lua cache. used_memory is more than your values.
Senior

Staff

#8 — Why can Redis RSS remain high after deleting data?

Because RSS is what the OS has handed to the process, not what Redis is using. The allocator (jemalloc) keeps freed pages that are still partially occupied, or holds free memory for reuse, so deleting keys lowers used_memory but not used_memory_rss.

Why this happens

  • Allocator behaviour: jemalloc groups blocks by size class into runs/slabs. A slab can only be returned when all of its blocks are free. Deleting scattered keys leaves holes.
  • Mixed lifetimes and sizes: long-lived and short-lived keys of varied sizes interleave and pin each other's pages. Bad workloads: many sizes, high churn, keys written then partly deleted.
  • Peak memory: a past peak (big import, big key, big pipeline reply) grows the heap and it stays grown.
  • Copy-on-write: during RDB/AOF rewrite the child shares pages; parent writes duplicate pages. RSS inflates during the snapshot and drops after.
  • Transparent Huge Pages (THP): 2 MB pages make COW copy far more memory and prevent fine-grained release. Disable THP for Redis hosts.
  • used_memory_rss also includes allocator metadata, the Lua engine, and shared libraries.

Reading the numbers

SignalMeaning
mem_fragmentation_ratio > ~1.5 and stableFragmentation: RSS much larger than used. Candidate for defrag or a rolling restart.
ratio < 1.0Redis is swapping (RSS less than used): emergency, latency is already bad.
Large allocator_frag_bytes / allocator_rss_bytesWaste inside the allocator (fixable by active defrag)
rss_overhead_bytesProcess overhead outside the allocator

What to do

  1. Active defragmentation (jemalloc builds only): activedefrag yes with thresholds (active-defrag-ignore-bytes 100mb, active-defrag-threshold-lower 10, CPU bounds active-defrag-cycle-min/max). Redis moves live allocations into fuller pages online, trading some CPU.
  2. MEMORY PURGE asks jemalloc to release dirty pages (helps when memory is free but not returned).
  3. Rolling restart / failover: promote a freshly synced replica (loads data compactly) and restart the old node. The cheapest way to get compact memory for big drops.
  4. Prevent: avoid mixed-size, high-churn patterns; cap value sizes; use lazyfree-* options; keep headroom (maxmemory well below RAM) knowing that fragmentation of 10–30% is normal.
  5. Disable THP, keep vm.overcommit_memory=1.
Staff-level answer"RSS is the allocator's footprint, not my data. Capacity planning should use RSS at peak plus fork headroom, not used_memory. High RSS after deletes is normal; it only matters if the ratio is high and the box is short of RAM, and then I defrag online or fail over to a fresh replica."

09Redis Persistence

Mental model: Redis is memory-first. Disk is a recovery mechanism, written either as periodic photographs (RDB) or as a running diary (AOF).

Beginner

#9 — Is Redis persistent?

It can be, but only if you configure it. Redis stores data in RAM and can save it to disk with RDB snapshots, an AOF (append-only file), both, or neither. With neither, a restart means an empty database.

RDB snapshot

A compact point-in-time file (dump.rdb) written every so often: save 3600 1 300 100 60 10000 means "after 3600 s if 1 key changed, or 300 s / 100 changes, or 60 s / 10000 changes."

AOF

A log of every write command, replayed on restart. You choose how often it hits disk (always, everysec, no).

None

Pure cache mode. Fastest, no disk I/O, nothing to recover.

Common mistakeAssuming "it is Redis, so it is a database that keeps my data" and finding a freshly restarted instance empty. Check CONFIG GET save and CONFIG GET appendonly.

Persistence protects against restart or crash of this process. It is not backup (copy the files elsewhere) and not high availability (use replication for that).

Senior

#9 — RDB vs AOF?

RDB is a compact periodic snapshot: fast restart, small files, but you lose everything since the last snapshot. AOF logs every write: much smaller loss window, but bigger files and slower restart. Most production setups use AOF (with the RDB preamble), or RDB on replicas only.

  • fork() cost is proportional to memory (page table copy): on bare metal often tens of ms per GB, worse on some hypervisors. Watch latest_fork_usec. A 50 GB instance can stall for seconds.
  • Copy-on-write memory growth during the child's life is proportional to the write rate. Leave RAM headroom; disable THP.
  • everysec fsyncs in a background thread. If the disk is slow, Redis may delay writes up to 2 seconds rather than block indefinitely (check aof_delayed_fsync).
  • Combine both (recommended by Redis for durability): AOF for recent data, RDB preamble for fast load, RDB files for backups.
  • Persistence on a master pauses nothing in steady state, but replicas can do it instead (see Staff).
Staff

Usually no on the master, because a cache is rebuildable and persistence costs latency and complexity. But "no persistence" shifts risk to cold restarts. Consider RDB on a replica for warm starts, and AOF only when the data stops being a cache.

10Redis Transactions & Atomicity

Mental model: one command is atomic. A sequence of commands is atomic only if you explicitly make it so (MULTI/EXEC, or a script), and even then it is not an RDBMS transaction (no rollback).

Beginner

#10 — Are Redis commands atomic?

Yes. Each single command runs to completion with nothing else interleaved, because commands execute one at a time on one thread. But two separate commands are not atomic together.

Atomic single commands you will use constantly: INCR/DECR, SET NX, GETSET/GETDEL, LPUSH/RPOPLPUSH, HINCRBY, ZADD, SADD. Even multi-element commands (MSET, SUNIONSTORE) are atomic as one command.

Senior

#10 — What are MULTI/EXEC?

MULTI starts queuing commands; EXEC runs the whole queue back-to-back with no other client's command in between. WATCH adds optimistic locking. There is no rollback.

What it gives you and what it does not

  • Isolation: the queued commands are executed contiguously. Other clients cannot interleave.
  • Atomicity of execution, not of failure: if one command errors at runtime (e.g. INCR on a string), earlier ones stay applied. If Redis crashes mid-EXEC, persistence may have captured part (AOF stores the transaction wrapped in MULTI/EXEC and recovery discards an incomplete one).
  • No reads that drive logic: replies arrive only at EXEC, so you cannot do "GET, then decide, then SET" inside it. For that, use WATCH (optimistic) or Lua.
  • WATCH pattern:
WATCH balance:42
bal = GET balance:42          # read outside MULTI
MULTI
SET balance:42 (bal - 10)
EXEC                           # nil if someone changed it: loop and retry
  • Connection affinity: WATCH and MULTI state live on one connection. In a pool you must hold the same connection between WATCH and EXEC, and release it on every path (including errors). With multiplexed clients (StackExchange.Redis) use its condition-based transaction API instead.
  • Cluster: all keys in the transaction must be in the same hash slot.
  • Cost: queued commands consume memory and are still serial; a very large transaction blocks others like a long command does.
  • DISCARD abandons the queue; UNWATCH clears watches.
Staff

#10 — When would you use Lua/scripts instead of MULTI/EXEC?

When the logic needs to read values and branch on them atomically (compare-and-delete, check-and-decrement, token bucket), or to cut round trips. Scripts run entirely server-side in one atomic step; MULTI/EXEC cannot see intermediate results.

  • Safe lock release: delete only if the token matches.
  • Rate limiters (token bucket, sliding window) that read, compute, write.
  • Inventory / quota: decrement only if stock > 0.
  • Atomic multi-structure updates (move between a ZSET and a HASH).
  • Versioned cache writes (topic 6).

Rules and gotchas

  • Declare every key in KEYS, pass values in ARGV. Required for Cluster routing and ACLs, and lets Redis reason about keys.
  • Never loop over unbounded data. A script blocks the event loop; after busy-reply-threshold (default 5 s, a.k.a. lua-time-limit) other clients get BUSY errors, and only SCRIPT KILL (if no writes yet) or SHUTDOWN NOSAVE help.
  • Determinism: since Redis 5, scripts replicate by effects (the commands they ran), so TIME or random calls are allowed. Older versions required determinism.
  • Caching and deploy: EVALSHA hash lookup; scripts are not persisted across restarts (script cache is lost), so clients must fall back to EVAL/SCRIPT LOAD on NOSCRIPT. Redis 7 Functions (FUNCTION LOAD) are named, persisted and replicated, a better fit for shared libraries.
  • Atomic but not isolated from failure: design scripts to be idempotent and check before writing.
  • Fewer scripts is better. Every script is code running inside the datastore with no debugger.
Staff-level answer"Default to single atomic commands. Use MULTI/EXEC when I only need isolation of independent writes. Use a script when logic depends on current values or I need to avoid WATCH retries under contention, keep it tiny and O(1), pass keys explicitly, and prefer Functions in Redis 7+."

11Pipelining

Mental model: Redis answers in microseconds; the wire takes hundreds of them. Pipelining stops you waiting for the wire between commands.

Beginner

#11 — What is Redis pipelining?

Sending many commands without waiting for each reply, then reading all the replies together. The commands are the same; you just stop paying a network round trip per command.

# redis-cli
printf 'SET a 1\r\nSET b 2\r\nGET a\r\n' | redis-cli --pipe

# client library (pseudocode)
pipe = redis.pipeline()
for k in keys: pipe.get(k)
values = pipe.execute()           # one network flush, N replies in order

Typical uses: bulk loading, fetching many keys, setting many keys with TTL, sending many INCRs. Pipelining is not a transaction: other clients' commands can interleave between yours (use MULTI inside the pipeline if you need isolation).

Senior

#11 — Why does pipelining improve performance?

Because the cost of a Redis command is dominated by network latency and system calls, not by execution. Pipelining amortises both: one round trip for many commands, and far fewer read()/write() syscalls on both sides.

Two savings

  1. Round-trip time (RTT). Execution takes ~1–10 µs; RTT inside a datacenter is ~100–500 µs, across AZs 1–2 ms. Without pipelining a client does at most 1/RTT commands per second per connection (2,000 ops/s at 0.5 ms). 100 clients would be needed to reach 200k ops/s.
  2. Syscalls and context switches. Each unpipelined command costs the server a read() and a write() (and an epoll wakeup). With a pipeline, one read() pulls many commands, and replies are coalesced into one write(). This is why pipelining can make the server do several times more ops/s, not just the client.

Mechanics

  • The server processes commands in order and appends replies to the client's output buffer; the client reads them in order. Reply N matches command N.
  • TCP provides the pipeline: a write buffer, no extra protocol.
  • Throughput rises almost linearly with batch size until CPU becomes the limit (often 5–10x for small commands), then flattens.
  • Not atomic, not isolated: partial failures possible; a failed command does not stop the next ones.
  • Higher-level alternatives for the same goal: MGET/MSET, HMGET, variadic SADD/DEL, or a Lua script (also atomic).
RelatedMultiplexed clients (StackExchange.Redis, Lettuce, ioredis auto-pipelining) pipeline across callers automatically over one connection, so you often get pipelining benefits without writing a batch.
Staff

#11 — Can pipelining make Redis slower?

Yes, if batches get too large or the pipeline contains slow commands. You trade latency for throughput and push memory pressure onto the server and client, and you can hurt other clients sharing the instance.

How it backfires

  • Server reply buffering. Replies for the whole batch sit in the client's output buffer until the client reads them. A 1M-command pipeline of GET on 10 KB values is 10 GB of buffered replies. client-output-buffer-limit normal is unlimited by default, so memory balloons, possibly past maxmemory and into OOM.
  • Head-of-line blocking for others. The server executes a long pipeline command by command. Other connections interleave only when the event loop gets to them; a giant batch of O(N) commands (or one slow command in it) delays everyone's tail latency.
  • Client-side memory and latency. The client must buffer commands before sending and replies after. The first command in the batch now waits for the last one before its result is usable.
  • One slow command ruins the batch. A single SMEMBERS on a big set delays all replies behind it.
  • Errors and retries. Partial failure in a huge batch: which commands ran? Retrying non-idempotent commands (INCR, LPUSH) double-applies.
  • Timeouts. A pipeline that needs 5 s total with a 2 s client timeout fails after doing the work.
  • Cluster. Keys in one pipeline map to different nodes; the client must split per node, which negates simple batching and can serialise nodes unless done in parallel. Cross-slot pipelines in naive clients error out.
  • TCP and kernel buffers. Writing a huge batch without reading replies can deadlock a naive client when send and receive buffers both fill.

How I use it

  1. Chunk: batches of 100–1,000 commands (tune against p99 of other traffic).
  2. Limit payload size per batch (e.g. 1–4 MB), not just command count.
  3. Prefer native multi-key commands (MGET, HMGET) for reads of the same type.
  4. Keep pipelines off the hot dedicated connection in pool-based clients, so a slow batch does not block user requests.
  5. Set client-output-buffer-limit and monitor mem_clients_normal and client_recent_max_output_buffer.

12Connection Pooling & Multiplexing

Mental model: a connection is a lane to a single-threaded server. More lanes does not mean more speed once the server is the bottleneck; fewer lanes than concurrent demand means queuing in your app.

Beginner

#12 — Why use Redis connection pooling?

Opening a connection is slow and expensive (TCP handshake, maybe TLS, AUTH, SELECT). A pool keeps a few connections open and reuses them, so each request borrows one instead of paying setup cost.

  • Latency: a new TCP + TLS connection can cost several RTTs, much more than the command itself.
  • Protect Redis: maxclients defaults to 10,000 and each connection uses file descriptors and buffers. Unbounded connection creation can exhaust them.
  • Predictability: a pool caps concurrency per app instance.
  • Thread safety: a plain connection can only run one command at a time (or you interleave replies wrongly). Pools give each thread its own connection.
# typical (Jedis / go-redis / redis-py style)
pool = ConnectionPool(host, port, max_connections=20)
r = Redis(connection_pool=pool)
r.get("k")        # borrows a connection, runs, returns it
.NET noteStackExchange.Redis does not use a classic pool: share one ConnectionMultiplexer per app (singleton). See the Senior answer for why.
Senior

#12 — What happens if your connection pool is too small?

Requests queue inside your application waiting for a free connection. Latency rises and timeouts appear even though Redis itself is idle, so it looks like "Redis is slow" when it is your pool.

Symptoms

  • Errors like "Could not get a resource from the pool" (Jedis), "redis: connection pool timeout" (go-redis), pool wait-time metrics rising, thread dumps full of threads parked on pool borrow.
  • Latency measured in the app far above SLOWLOG or Redis-side latency; Redis CPU is low.
  • Throughput capped at about pool_size / avg_latency.
  • Blocking commands (BLPOP, XREAD BLOCK, SUBSCRIBE) and WATCH-transactions hold a connection for a long time, quietly shrinking the pool.
  • Connection leaks (borrowed, never returned after an exception) drain the pool over hours.

Sizing with Little's law

busy connections = requests per second × average latency. At 5,000 req/s and 2 ms per call, ~10 connections are busy on average. Provision 2–3x for bursts and variance (20–30), not 5 and not 500.

needed ≈ peak_rps * p99_latency_seconds * safety(2..3)
example: 5000 * 0.004 * 2 = 40 → pool of ~40 per app instance
(then multiply by instances to check Redis' total connection count)

Multiplexing (StackExchange.Redis, Lettuce, ioredis)

One connection carries interleaved commands from many callers, pipelined, and responses are matched by order. Very efficient for normal commands (no pool wait, automatic batching). Limits: blocking commands and WATCH transactions need dedicated connections (don't use BLPOP on the shared multiplexer), one slow reply delays those behind it on that socket, and a single connection is limited by its own throughput. Timeouts in .NET often come from thread-pool starvation or synchronous-over-async code, not from Redis.

Staff

#12 — Why can increasing the pool size make things worse?

Redis executes commands on one thread, so extra connections do not add processing capacity; they only add queueing inside Redis, memory, and connection storms. When Redis is the bottleneck, a bigger pool turns a slow dependency into a dead one.

Mechanisms

  • One executor. If Redis CPU is saturated, 100 or 1,000 connections still share one core's worth of command execution. By Little's law, in-flight requests = throughput × latency; with throughput capped, extra concurrency raises latency linearly, so timeouts and retries start.
  • Retry amplification. Timeouts trigger retries, which add more concurrent requests, which add more latency. A classic metastable failure.
  • Per-connection cost. Each connection has input/output buffers (tens of KB or more), a file descriptor and kernel socket memory. Thousands of connections cost real RAM and slower epoll scans. TLS adds CPU per connection and handshake cost.
  • Fleet multiplication. Total connections = pods × pool size × nodes (in Cluster each pool connects to every node). 200 pods × 50 × 6 nodes = 60,000 connections, far above maxclients and file-descriptor limits. A deploy or failover makes every pod reconnect at once, a connection storm that can keep Redis from recovering.
  • Pushes the bottleneck downstream. A bigger pool lets more concurrent requests through to Redis, which then fails for everyone instead of shedding load at the edge.
  • Hides real problems. Raising pool size "fixes" symptoms from slow commands, big keys or hot keys by letting more work pile up behind them.

What to do instead

  1. Find the real bottleneck first: pool wait time vs Redis latency (LATENCY, SLOWLOG, CPU). If Redis is slow, fix commands/keys; if the pool waits while Redis is idle, enlarge moderately.
  2. Size from math (Little's law) and cap the fleet total well below maxclients.
  3. Bounded waiting plus backpressure: a short pool-acquire timeout, circuit breaker and load shedding, so the app fails fast instead of queueing.
  4. Retry with backoff and jitter; limit retry budget.
  5. Use multiplexing or pipelining so concurrency is achieved with few connections.
  6. Scale Redis horizontally (Cluster, read replicas) when one core is the limit; consider I/O threads for socket-bound loads.
  7. Proxy layer (Envoy, Twemproxy, Redis Enterprise proxy) to collapse thousands of client connections to few server connections.
  8. Monitor connected_clients, rejected_connections, total_connections_received rate (storm detector).

13Redis Replication

Mental model: a replica is a follower that replays the master's write stream. It is a copy for availability and read scaling, not a quorum.

Beginner

#13 — What is Redis replication?

One Redis node (master/primary) accepts writes and streams them to one or more replicas, which hold a copy of the data. Replicas serve reads and can take over if the master dies.

Why use it

  • High availability: a replica can be promoted if the master fails (with Sentinel or Cluster).
  • Read scaling: spread read-heavy traffic across replicas (accepting staleness).
  • Safer persistence: let a replica do snapshots/AOF so the master does not.
  • Backups and maintenance without touching the master.
replicaof 10.0.0.5 6379     # in redis.conf, or at runtime: REPLICAOF host port
INFO replication            # role, connected_slaves, master_repl_offset, lag
REPLICAOF NO ONE            # promote this replica to master
Senior

#13 — Is Redis replication synchronous?

No. The master applies a write, replies OK to the client, and streams the command to replicas afterwards. A write can be acknowledged yet exist only on the master. WAIT lets a client wait for replicas, but it is still not a quorum commit.

How a replica syncs (PSYNC)

Consequences of async replication

  • Lost acknowledged writes on failover: if the master dies before streaming a write, the promoted replica never had it.
  • Stale reads: a replica can lag. A client that writes then reads from a replica may not see its own write.
  • Backlog sizing: repl-backlog-size (default 1 MB) decides whether a reconnect gets a partial or full resync. Too small on a write-heavy master means frequent full syncs (fork + RDB + bandwidth).
  • Full sync is expensive: master fork, CPU, network, and a replica memory spike; many replicas syncing at once multiplies cost. Diskless replication (repl-diskless-sync, default yes since 7.0) streams the RDB straight to the replica sockets.
  • Replication buffer / output buffer limit: a slow replica can exceed client-output-buffer-limit replica 256mb 64mb 60 and be disconnected, which triggers another full sync (a classic loop on big, busy masters).
  • Expiry: replicas rely on the master's DEL for expiry.
  • Writes to a replica are rejected (replica-read-only yes).
Monitormaster_repl_offset vs each replica's offset; INFO replication lag; sync_full, sync_partial_ok/err counters in INFO stats.

14Redis Sentinel

Mental model: Sentinel is a small voting cluster that watches one master/replica set and promotes a replica when the master is gone. It provides failover and discovery, not sharding.

Beginner

#14 — What is Sentinel?

Sentinel is a separate set of processes that monitors Redis master and replicas, automatically promotes a replica when the master fails, and tells clients where the current master is.

Sentinel does four jobs

  • Monitoring: pings the master, replicas and other sentinels.
  • Notification: alerts via pub/sub and scripts.
  • Automatic failover: promotes the best replica and reconfigures the others.
  • Configuration provider: clients ask SENTINEL get-master-addr-by-name mymaster instead of hardcoding an address.

You need at least three sentinels, on independent machines. Two cannot form a majority after one fails.

Senior

#14 — What happens during Sentinel failover?

A sentinel notices the master is unreachable (SDOWN); a quorum agrees (ODOWN); sentinels elect a leader by majority vote; the leader picks the best replica, promotes it, reconfigures the others, and publishes the new master. Clients then reconnect.

Details that matter

  • Quorum vs majority. sentinel monitor mymaster host 6379 2: quorum 2 = how many sentinels must agree the master is down (ODOWN). The failover leader election still needs a majority of all sentinels. With 3 sentinels, losing 2 means no failover even if quorum is 1.
  • Replica selection: skip replicas that were disconnected too long; prefer lowest replica-priority (0 = never promote), then the largest replication offset (most data), then lowest run ID.
  • Config epoch: each failover bumps a version number. The highest epoch wins when sentinels reconcile, preventing two competing configurations.
  • Old master returns: Sentinel reconfigures it as a replica of the new master. Anything it accepted while isolated (split-brain writes) is discarded. Mitigate with min-replicas-to-write 1.
  • Clients must be Sentinel-aware (ask Sentinel for the master, subscribe to +switch-master) and handle connection errors with retries. Without that, failover happens but your app keeps hitting the dead address.
  • Tuning: down-after-milliseconds (too low = flapping on GC or network blips), failover-timeout, parallel-syncs (how many replicas resync at once with the new master).
  • Write unavailability window: from master failure to client reconnect, writes fail. Design retries and idempotency.
  • Docker/NAT: announce correct IPs (sentinel announce-ip) or sentinels will advertise unreachable addresses.

15Redis Cluster

Mental model: the keyspace is cut into 16,384 slots. Each slot belongs to exactly one master. Everything else (routing, resharding, failover) is slot bookkeeping.

Beginner

#15 — What is Redis Cluster?

Redis Cluster shards data across several masters, each owning a range of 16,384 hash slots, with replicas for failover. It scales memory and write throughput beyond one machine, and handles failover without Sentinel.

  • Every key belongs to one slot; every slot lives on one master at a time.
  • Nodes gossip to detect failures. If a master is declared failed by a majority of masters, its replica is promoted.
  • Only database 0 exists. Some commands are restricted to a single slot.
Senior

#15 — How does Redis know which node owns a key?

slot = CRC16(key) mod 16384 (using only the {hash tag} if the key has one). The client keeps a slot-to-node map, sends the command to the owner, and corrects its map when a node answers MOVED.

Mechanics worth knowing

  • Hash tags: the first {...} with non-empty content is hashed. {user:42}:cart and {user:42}:profile land in the same slot, which makes multi-key operations legal.
  • Resharding: slots are moved one at a time (redis-cli --cluster reshard). For each key the source MIGRATEs it to the target. While a slot is migrating, the source answers ASK for keys already moved.
  • Failure detection: a node marks another PFAIL after cluster-node-timeout without a reply; when a majority of masters report it, it becomes FAIL, and its replica gets elected by the masters and promoted.
  • Availability rule: with cluster-require-full-coverage yes (default) the cluster stops serving if any slot lacks an owner. Set to no if partial availability is better for you.
  • Replicas serve reads only after READONLY and with possible staleness.
  • Smart clients are required (StackExchange.Redis, Lettuce, go-redis, redis-py cluster mode, etc.). Plain clients see only redirects.
  • Gossip scale: the bus is O(N²)-ish chatter, so keep clusters to hundreds of nodes at most, typically far fewer.
Staff

#15 — What happens if your operation touches multiple keys?

If all keys hash to the same slot it works. If not, the node rejects it with -CROSSSLOT Keys in request don't hash to the same slot. This applies to MGET, MSET, SUNION, MULTI/EXEC, Lua and more. You must change the key design or give up atomicity.

Options, in order of preference

  1. Hash tags for entities that must be operated on together. Tag by the entity id ({order:991}:items, {order:991}:status). Atomic ops then work. Risk: a very large or hot tag creates a fat shard; do not tag by something low-cardinality (tenant with 90% of traffic).
  2. Redesign the data model so each operation touches a single key (denormalise, use one hash with fields instead of many keys).
  3. Scatter-gather in the client: issue separate commands per node in parallel (pipelined per node) and merge. Not atomic, but fine for reads. Many clients do this for MGET automatically (check yours).
  4. Sequences with compensation for writes: no atomic multi-shard transaction exists. Use idempotent steps, an outbox, or put the data in a store with transactions.
  5. Scripts must receive all keys via KEYS and they must share a slot; touching undeclared keys is a correctness bug.

Special cases

  • During resharding a multi-key command on a slot that is partly migrated returns -TRYAGAIN; retry with backoff.
  • Pub/Sub: classic PUBLISH is broadcast to every node (bandwidth and CPU grow with cluster size). Redis 7 sharded Pub/Sub (SPUBLISH/SSUBSCRIBE) routes by slot.
  • KEYS, SCAN, FLUSHALL operate per node; iterate over all masters yourself.
  • Transactions with WATCH need all keys in one slot.
  • Big tags create hot shards: measure key and traffic distribution per slot (CLUSTER COUNTKEYSINSLOT, per-node ops/s).
Staff-level answer"Design for Cluster up front: one entity, one slot via hash tag; cross-entity work is eventually consistent. Anything needing atomicity across entities belongs in a transactional store."

16Hot Keys

Mental model: sharding spreads keys, not requests. A single key can only ever live on one node, so one popular key caps at one core regardless of cluster size.

Beginner

#16 — What is a hot key?

A key that gets a disproportionately large share of traffic, for example the homepage banner, a celebrity profile, a global counter, or a viral product during a flash sale.

  • Even if the key is tiny and every command is fast, enough requests per second on one key saturate the single Redis thread that owns it, or the NIC of that node.
  • Typical causes: traffic spikes (events), popular entities (power law distribution), global configuration or feature-flag keys read on every request, a single counter or lock updated by everyone.
  • Symptoms: one node at high CPU or network while the others idle, rising latency for all keys on that node, timeouts for unrelated traffic.
Hot key vs big keyHot = many requests. Big = a lot of data. They are independent: a tiny key can be hot, a huge key can be cold. A key that is both is the worst case.
Senior

#16 — Why is a hot key dangerous in Redis Cluster?

Because the cluster scales by distributing slots, and a key cannot be split across nodes. One shard absorbs all the load, the rest sit idle, and adding nodes does nothing for it.

Why it is worse than it looks

  • Collateral damage: every other key on that node shares the same single thread, so unrelated requests slow down or time out.
  • Network saturation: a hot key with a large value can saturate the NIC before the CPU (50k × 20 KB = 1 GB/s).
  • Failover does not help: the replica takes the same load after promotion, and may be colder or slower, so it can collapse right after failover.
  • Replicas help only if reads go there (READONLY), and you may have only one or two per shard.
  • Cascading effects: timeouts cause retries, which add load; clients also hold connections open longer, shrinking pools (topic 12).
  • Hidden by averages: cluster-wide CPU is low; only per-node and per-key metrics show it.

Detection

  • Per-node CPU, ops/s and bandwidth skew (alert on max vs median).
  • redis-cli --hotkeys (needs an LFU maxmemory-policy, uses OBJECT FREQ), OBJECT FREQ key.
  • MONITOR sampled briefly (expensive, can halve throughput; use for seconds only), or redis-cli --hotkeys / proxy-level stats.
  • Client-side instrumentation: count calls per key class / top-N keys.
  • INFO commandstats and CLIENT LIST to attribute load.

17Distributed Locks

Mental model: a Redis lock is a lease with an expiry, not a guarantee of exclusion. It is good at "avoid doing the same work twice" and dangerous for "never corrupt this resource".

Beginner

#17 — Why use a Redis lock?

When several app instances must not do the same thing at the same time: run a scheduled job once, process an order once, update a shared resource one writer at a time. In-process locks cannot do that across servers; a shared Redis key can.

  • Examples: a cron job running on 5 pods should execute on only one; payment capture for order 42; cache rebuild for a hot key; leader election.
  • Why Redis: shared by all instances, fast, and SET key value NX PX ttl sets-if-absent with an expiry in one atomic step.
  • Why a TTL: if the holder crashes, the lock must free itself.
SET lock:report:daily  worker-7f3a  NX  PX 30000
# OK   → I hold the lock for 30 s
# nil  → someone else holds it
Senior

#17 — How do you safely acquire a Redis lock?

Acquire with one atomic SET key token NX PX ttl, using a unique random token per holder. Release with a script that deletes only if the token still matches. Renew while working, retry with jittered backoff, and use fencing tokens if correctness matters.

-- release.lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
end
return 0

-- renew.lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("PEXPIRE", KEYS[1], ARGV[2])
end
return 0

Practical rules

  • TTL > worst-case work time, or renew. Too short means two holders; too long means slow recovery after a crash.
  • Backoff with jitter on retry, with a max wait. Do not spin.
  • Do not use eviction policies that can evict lock keys (allkeys-*); dedicate an instance or use noeviction/volatile-* carefully.
  • Make the protected work idempotent wherever possible. The lock is an optimisation, idempotency is the safety net.
  • Libraries: Redisson (Java, with watchdog), RedLock.net / StackExchange.Redis LockTake/LockRelease, redsync (Go). Prefer them over hand-rolled code.
  • Fencing token: if the resource can validate it, increment a counter (INCR) on each acquire and pass it with every write.

#17 — What's wrong with a naive Redis distributed lock?

Naive versions fail in several ways (non-atomic acquire, no TTL, unsafe release). Even a correct single-node lock is not a mutual-exclusion guarantee: pauses, expiry and failover can give two clients the lock at once, so it is only safe for efficiency, not for correctness, unless the resource enforces fencing.

Fundamental problems, even if the code is perfect

  • Process pauses and clock jumps: GC, VM migration, CPU starvation, slow disk, network delay. The holder thinks it still has time. TTL-based locks assume bounded pauses.
  • Failover loses the lock: replication is async. The master grants the lock, dies before replicating the key, a replica is promoted, and another client acquires the same lock. Two holders.
  • Eviction or restart of the lock node (non-persistent, allkeys-lru) silently releases locks.
  • No fencing: with plain Redis the lock has no monotonic token the resource can check.

Redlock and the debate

Redlock (by Redis's creator) acquires the lock on a majority of N (typically 5) independent masters within a short timeout, and treats the lock as valid for TTL minus elapsed time minus a drift allowance. It survives single-node failover loss. Martin Kleppmann's critique: it relies on timing assumptions (bounded pauses, clock drift), and without fencing tokens it is still unsafe for correctness. else: allow

#18 — What's wrong with a simple INCR + EXPIRE implementation?

The two commands are not atomic, so a failure between them leaves a counter with no TTL that never resets and blocks the user permanently. It also has the fixed-window boundary burst, no good answer for Redis failure, and several hot-key and clock pitfalls.

Concrete problems

  1. Non-atomic INCR then EXPIRE. If the process crashes, times out, or the connection drops after INCR returned 1 but before EXPIRE, the key lives forever. Once it passes the limit, that user is blocked until someone deletes the key. Keys without TTL also leak memory.
  2. "Set expiry only on first hit" is still racy. The count == 1 check relies on that one request surviving to run EXPIRE. A retry, concurrent first hits, or a lost reply breaks it.
  3. Calling EXPIRE on every request (the other common variant) turns the window into "reset after inactivity": a client that sends steadily never gets a reset and a client that stops is cleared. That is a different limiter than intended.
  4. Boundary bursts (2x limit across two windows).
  5. Time source skew. If window id is floor(now/60) computed in each app server, clock differences put the same request in different windows. Use Redis TIME in a script or tolerate skew.
  6. No distinction between rejected and allowed. INCR counts rejected requests too (harmless for fixed windows, harmful if you later add penalties or compute remaining quota).
  7. Redis failure policy missing. If Redis is down, do you fail open (allow everything, risking overload) or fail closed (reject everything, causing an outage)? Pick per endpoint; fail-open with a local fallback limiter is common.
  8. Hot key. One key per tenant or IP under attack is a hot key on one shard (topic 16). Layer a local in-memory limiter in front.
  9. Cluster routing. Multi-key limiter scripts must keep all keys in the same slot with hash tags.
  10. Precision and fairness. Per-instance retries and clients retrying immediately after a 429 can amplify load; send Retry-After and use jittered client backoff.

Fixes

# 1) atomic: set TTL only if none (Redis 7.0+), in a transaction
MULTI
INCR rl:u42:{window}
EXPIRE rl:u42:{window} 60 NX
EXEC

# 2) or one Lua script that does INCR + PEXPIRE-on-first + compare with limit
# 3) or avoid the issue: one key per window, window id in the key name,
#    TTL = 2 × window, and the cost of a missed EXPIRE is only a bounded leak
# 4) better algorithm: token bucket / sliding window counter inside a script

20Pub/Sub

Mental model: a radio broadcast. If your receiver is on, you hear it. If it is off, the message is gone, and the station keeps no recording.

Beginner

#20 — What is Redis Pub/Sub?

A messaging feature where publishers send messages to named channels and every client currently subscribed to that channel receives them immediately. Messages are not stored.

SUBSCRIBE news            # connection now only listens
PSUBSCRIBE news:*         # pattern subscription
PUBLISH news "hello"      # returns number of receivers

Good for live notifications, chat presence, websocket fan-out, cache invalidation hints to local caches. Not for work that must happen.

Senior

#20 — Is Redis Pub/Sub durable?

No. Delivery is at-most-once: nothing is stored or retried. A subscriber that is disconnected, slow or restarting loses messages permanently, and a failover can drop them too.

Behaviours that bite

  • No persistence, no replay, no ack. If a subscriber reconnects, it only gets future messages.
  • Slow subscribers get disconnected. Messages queue in the client's output buffer; the default client-output-buffer-limit pubsub 32mb 8mb 60 kills a client that exceeds 32 MB, or 8 MB for 60 s. Messages in the buffer are lost.
  • Subscribed connections are special: in RESP2 a connection that has subscribed can only issue (un)subscribe/ping commands, so use dedicated connections (in pools and multiplexers, this matters).
  • Network blips lose messages silently; clients must resubscribe on reconnect and cannot know what they missed.
  • Replication: PUBLISH is propagated to replicas, which forward to their own subscribers, but nothing is stored for catching up.
  • Cluster: classic PUBLISH goes to all nodes via the cluster bus (cost grows with cluster size). Redis 7 sharded Pub/Sub (SPUBLISH/SSUBSCRIBE) keeps traffic within a shard.
  • Pattern subscriptions cost O(number of patterns) per publish; many patterns slow down publishing.
  • No consumer groups: every subscriber gets every message; there is no work sharing.
  • Keyspace notifications use Pub/Sub, so they are lossy too.
Neveruse Pub/Sub for payments, order events, job dispatch or anything where "missed" means "wrong".
Staff

#21 — Redis is slow. What do you check?

  8. Client side: pool exhausted, thread starvation, GC pauses, DNS or TLS handshakes.
  9. Recent change: deploy, traffic increase, new feature, new cron job.

#21 — How would you diagnose this systematically?

Define the symptom and scope, split the request path into client, network, queue and server, bisect with measurements instead of guessing, correlate with events (deploys, saves, traffic), form a hypothesis with a predicted signal, test it, fix, and add alerting so the next one is caught early.

The method

  1. Characterise. Percentile (p50 vs p99), which operations, which nodes, steady or periodic (a spike every 60 s smells like cron/expiry/save), gradual or sudden. Write it down.
  2. Know what each tool measures. SLOWLOG records execution time only; it will not show queueing behind another command, network, or client delay. If app latency is high and SLOWLOG is empty, the delay is outside command execution (queue, network, client).
  3. Split the path. Run redis-cli --latency from the same host as the app. High there = network/Redis; low there but high in the app = client/pool/serialisation.
  4. Apply the USE method to each resource (utilisation, saturation, errors): Redis CPU (single thread), memory (swap, fragmentation, maxmemory), network (bandwidth, retransmits), disk (fsync, iowait), connections (maxclients, buffers).
  5. Correlate events. Overlay deploys, traffic, latest_fork_usec, expired_keys rate, evicted_keys, sync_full, failovers on the latency graph. Latency spikes that line up with one of them point to the cause.
  6. Hypothesis, prediction, test. "If it is the AOF rewrite, spikes align with aof_rewrite_in_progress and LATENCY HISTORY fork." Check, do not assume.
  7. Mitigate, then fix. Stop the bleeding (shed load, kill a bad client with CLIENT KILL, failover to a replica, disable a feature), then fix the root cause (key redesign, config, capacity).
  8. Verify and prevent. Confirm the metric recovered; add dashboard and alert; add the case to a runbook; load-test the fix.

Dashboards worth having before the incident

  • Per node: CPU (user/sys), instantaneous_ops_per_sec, used memory vs maxmemory, RSS, fragmentation, connected/blocked clients, network in/out, evicted/expired keys per second, hit ratio, latest_fork_usec, replication lag/offset, latency percentiles per command, slowlog count.
  • Client side: Redis call latency percentiles, pool wait time and in-use connections, timeouts, retries.
  • Per-key-class counters to spot hot keys and big values.

22Big Keys

Mental model: the single thread handles one command at a time, so a command's cost grows with the size of the key it touches. Big keys make every operation on them, and everything queued behind them, slow.

Beginner

#22 — What is a big key?

A key whose value is very large: a string of many KB or MB, or a collection (hash, list, set, sorted set, stream) with hundreds of thousands or millions of elements.

  • Rough thresholds (they vary by workload, but commonly used): strings above ~10 KB, collections with more than ~5,000–10,000 elements, anything over ~1 MB total deserves a look.
  • Typical origins: one hash holding every user's data, a list or sorted set that was never trimmed (all events, all followers), a cached JSON blob that grew with the data, a stream with no MAXLEN.
  • Find them: redis-cli --bigkeys, --memkeys, MEMORY USAGE key, offline RDB analysis.
redis-cli --bigkeys -i 0.1       # SCAN-based, throttled
redis-cli --memkeys

HLEN myhash   SCARD myset   ZCARD myzset   LLEN mylist   XLEN mystream   STRLEN mystr

#22 — Why are big keys dangerous?

Operations on them take long on the single thread, blocking every other client; they spike memory and network; and they make persistence, replication, expiry, eviction, deletion and cluster balancing all worse.

23Big Picture: Redis as a Distributed System

Everything above is one system seen from different sides. This section ties the pieces into a single model you can reason with in an interview or a design review.

Synthesis

Redis as a distributed system: layers, guarantees and failure modes

Redis is a fast, single-writer-per-shard, in-memory data store with asynchronous replication, probabilistic failure detection and best-effort durability. It is an AP-leaning, latency-optimised building block, not a consensus-based database, so you design around its guarantees instead of assuming them.

Design principles that follow

  1. Know the system of record. For every key class, state where the truth lives and how Redis is rebuilt. If Redis is the truth, state the accepted loss window.
  2. Put a TTL and a bound on everything. Time and size limits turn silent leaks into predictable load.
  3. Keep commands O(1) or O(log N) with a limit. The single thread is a shared resource; protect it from yourself.
  4. Design keys for the cluster you will have. One entity, one hash tag; no unbounded keys; avoid hot keys through layered caching.
  5. Assume async everywhere. Replication, invalidation, expiry and failover are eventually consistent; design reads, retries and idempotency for that.
  6. Fail deliberately. Decide fail-open vs fail-closed for each Redis-backed feature; add timeouts, circuit breakers and bulkheads so a Redis problem cannot become a database outage.
  7. Separate concerns by instance. Cache, locks/rate limits, queues and sessions have different eviction, persistence and availability needs.
  8. Measure the tails. Percentiles per command, per node, per key class; client-side and server-side; alerts on skew, not averages.
  9. Prefer the simpler tool that meets the guarantee. Locks for correctness, event logs, and authoritative state belong in systems built for consensus and durability.

3Cache-asideRead: cache then DB then fill. Write: DB then invalidate. Eventually consistent; TTL is the safety net.
4TTLLazy + sampled expiry, not a timer; jitter TTLs; always set one; replicas follow the master's DEL.
5StampedeOne rebuild per key: single-flight + SWR + jitter; lock only when rebuild is expensive.
6InvalidationDelete after commit with retries or CDC; guard against stale refills (replica lag, versions); TTL backstop.
7Memory & evictionmaxmemory always; allkeys-lfu for caches; noeviction for state; separate instances.
8Memory optimisationPer-key overhead and fragmentation dominate small data; investigate top-down; RSS is not used_memory.
9PersistenceRDB = snapshots, AOF = log; cache can skip it, ideally persist on a replica; beware empty restart wiping replicas.
10AtomicityCommands atomic; MULTI = isolation without rollback; Lua for read-decide-write; keep scripts tiny.
11PipeliningSaves RTT and syscalls; chunk it (100–1,000); huge batches hurt memory and other clients.
12PoolsSize by Little's law; too small queues in the app, too large overloads Redis; multiplexing reduces the need.
13ReplicationAsync; PSYNC with backlog; WAIT/WAITAOF and min-replicas narrow, not remove, loss.
14SentinelHA for one shard: SDOWN, ODOWN, leader election, promotion; Cluster when you need to scale beyond one node.
15Cluster16384 slots, CRC16, MOVED/ASK; multi-key needs one slot via hash tags.
16Hot keysOne key = one core; near cache, key copies, sharded counters, replica reads.
17LocksSET NX PX token + Lua release; good for efficiency, not correctness; use fencing for integrity.
18Rate limitingAtomic updates, algorithm per burst needs, Redis TIME, explicit fail-open/closed.
19StreamsIn-memory log with groups and PEL; light queue, not Kafka; trim and make consumers idempotent.
20Pub/SubAt-most-once broadcast; use for hints, not for work.
21TroubleshootingSplit client / network / queue / server; SLOWLOG shows execution only; correlate with events.
22Big keysBound size and lifetime by design; bucket, paginate, UNLINK, enforce limits.

How to answer "design X with Redis" in an interview

  1. State the access patterns and the data's loss tolerance.
  2. Pick structure and key design (TTL, bound, hash tag).
  3. Name the consistency model and the invalidation or write path.
  4. Say how it scales (replicas, cluster, hot keys) and where it breaks.
  5. Say what happens when Redis is slow or down, and how you would know (metrics).

Notes reflect Redis 7.x–8.x behaviour. Defaults and thresholds (listpack limits, buffer limits, hz, timeouts) can change between versions and managed services, so confirm against your own CONFIG GET output. Latency and throughput figures are orders of magnitude, not benchmarks.
